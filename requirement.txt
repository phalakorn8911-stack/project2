# Requirement Document

# Smart Army Vehicle Maintenance Dashboard

## ระบบบริหารจัดการซ่อมบำรุงยานพาหนะอัจฉริยะสำหรับหน่วยงาน

---

## 1. ชื่อโครงการ

**Smart Army Vehicle Maintenance Dashboard**
หรือ
**ระบบบริหารจัดการซ่อมบำรุงยานพาหนะอัจฉริยะสำหรับหน่วยงาน**

---

## 2. ภาพรวมโครงการ

โครงการนี้เป็นระบบ Web Application สำหรับบริหารจัดการยานพาหนะและงานซ่อมบำรุงแบบครบวงจร โดยออกแบบในรูปแบบ Dashboard เพื่อให้เจ้าหน้าที่สามารถตรวจสอบสถานะยานพาหนะ การแจ้งซ่อม รอบการซ่อมบำรุง ใบงานซ่อม คลังอะไหล่ และรายงานต่าง ๆ ได้จากระบบเดียว

ระบบนี้มุ่งเน้นการบริหารจัดการเชิงสนับสนุน เช่น การดูแลทะเบียนยานพาหนะ การติดตามความพร้อมใช้งาน การตรวจสภาพก่อนใช้งาน การแจ้งซ่อม การติดตามงานซ่อม การจัดการอะไหล่ และการสร้างรายงานสำหรับผู้ดูแลหรือผู้บังคับบัญชา

ระบบจะมีโมดูล AI เป็นฟีเจอร์เสริม เพื่อช่วยสรุปประวัติซ่อม วิเคราะห์อาการเสียเบื้องต้น จัดระดับความเร่งด่วน และสร้างสรุปรายงาน โดย AI จะไม่เป็นแกนหลักของระบบ หาก AI ไม่พร้อมใช้งาน ระบบหลักยังสามารถทำงานได้ด้วย Rule-based Logic

---

## 3. ที่มาของปัญหา

ปัจจุบันการบริหารจัดการยานพาหนะในหน่วยงานมักมีปัญหาหลายด้าน เช่น ข้อมูลยานพาหนะกระจัดกระจาย การติดตามสถานะรถทำได้ล่าช้า ไม่มีระบบแจ้งเตือนรอบซ่อมบำรุง ประวัติการซ่อมไม่ต่อเนื่อง และการเบิกอะไหล่ไม่เชื่อมโยงกับใบงานซ่อม

ปัญหาสำคัญที่พบ ได้แก่

1. ข้อมูลยานพาหนะถูกจัดเก็บหลายที่ เช่น เอกสาร สมุดบันทึก หรือไฟล์ Excel ทำให้ค้นหายากและเสี่ยงต่อข้อมูลสูญหาย
2. เจ้าหน้าที่ไม่สามารถทราบสถานะรถแบบรวดเร็ว เช่น รถพร้อมใช้งาน กำลังซ่อม รออะไหล่ หรือเกินรอบซ่อม
3. การตรวจสอบรอบซ่อมบำรุงยังต้องอาศัยการจำหรือการตรวจเอกสารด้วยตนเอง
4. ประวัติการซ่อมของรถแต่ละคันไม่เป็นระบบ ทำให้วิเคราะห์ปัญหาซ้ำหรือค่าใช้จ่ายสะสมได้ยาก
5. การแจ้งซ่อมและการมอบหมายงานช่างยังไม่มีระบบติดตามสถานะแบบเป็นขั้นตอน
6. คลังอะไหล่ไม่ได้เชื่อมกับงานซ่อม ทำให้ไม่ทราบต้นทุนจริงของการซ่อมแต่ละครั้ง
7. ผู้ดูแลหรือผู้บังคับบัญชาไม่มี Dashboard สำหรับดูภาพรวมความพร้อมของยานพาหนะ
8. การจัดทำรายงานต้องรวบรวมข้อมูลด้วยตนเอง ทำให้เสียเวลาและอาจเกิดความผิดพลาด

ดังนั้นจึงควรพัฒนาระบบ Smart Army Vehicle Maintenance Dashboard เพื่อรวมข้อมูลทั้งหมดไว้ในระบบเดียว และช่วยให้การบริหารจัดการยานพาหนะมีประสิทธิภาพมากขึ้น

## 4. วัตถุประสงค์ของโครงการ

1. เพื่อพัฒนาระบบ Web Application สำหรับบริหารจัดการข้อมูลยานพาหนะ
2. เพื่อจัดเก็บข้อมูลทะเบียนรถ ประเภทรถ สถานะรถ และเอกสารประจำรถอย่างเป็นระบบ
3. เพื่อช่วยติดตามรอบการซ่อมบำรุงตามระยะเวลา เลขไมล์ หรือชั่วโมงเครื่องยนต์
4. เพื่อให้ผู้ใช้งานสามารถแจ้งซ่อมและติดตามสถานะงานซ่อมได้
5. เพื่อให้ช่างสามารถจัดการใบงานซ่อม บันทึกอาการเสีย วิธีซ่อม และอะไหล่ที่ใช้
6. เพื่อบริหารจัดการคลังอะไหล่ เช่น รับเข้า เบิกออก และแจ้งเตือนอะไหล่ใกล้หมด
7. เพื่อสร้าง Dashboard แสดงภาพรวมสถานะยานพาหนะ งานซ่อม และค่าใช้จ่าย
8. เพื่อสร้างรายงานสำหรับผู้ดูแลหรือผู้บังคับบัญชา
9. เพื่อเพิ่มโมดูล AI สำหรับช่วยสรุป วิเคราะห์ และให้คำแนะนำเบื้องต้น
10. เพื่อออกแบบระบบให้สามารถขยายต่อในอนาคตได้ เช่น เปลี่ยน AI Model หรือแยก AI Server

8. ระบบ Mobile App แบบ Native

## 6. กลุ่มผู้ใช้งาน

ระบบจะมีผู้ใช้งานหลักดังนี้

### 6.1 Admin

ผู้ดูแลระบบ มีหน้าที่จัดการข้อมูลพื้นฐานทั้งหมด เช่น ผู้ใช้งาน สิทธิ์ หน่วยงาน ประเภทรถ และการตั้งค่าระบบ

### 6.2 เจ้าหน้าที่ยานยนต์

มีหน้าที่ลงทะเบียนรถ ตรวจสอบสถานะรถ จัดการรอบซ่อม รับเรื่องแจ้งซ่อม และติดตามภาพรวมของยานพาหนะ

### 6.3 พลขับหรือผู้ใช้งานรถ

มีหน้าที่ตรวจสภาพก่อนใช้งาน อัปเดตเลขไมล์ แจ้งปัญหาหรืออาการเสีย และติดตามสถานะการแจ้งซ่อมของตนเอง

### 6.4 ช่างซ่อม

มีหน้าที่รับใบงานซ่อม ตรวจสอบอาการเสีย บันทึกวิธีซ่อม ขอเบิกอะไหล่ อัปเดตสถานะงาน และแนบรูปก่อน/หลังซ่อม

### 6.5 หัวหน้าช่าง

มีหน้าที่มอบหมายงานให้ช่าง ตรวจสอบความคืบหน้า อนุมัติการใช้ชิ้นส่วนบางรายการ และตรวจคุณภาพก่อนปิดงาน

### 6.6 เจ้าหน้าที่คลังอะไหล่

มีหน้าที่จัดการข้อมูลอะไหล่ รับอะไหล่เข้า เบิกอะไหล่ออก ปรับยอดสต็อก และตรวจสอบอะไหล่ใกล้หมด

### 6.7 ผู้บังคับบัญชาหรือผู้บริหาร

มีหน้าที่ดู Dashboard รายงานภาพรวม ความพร้อมของยานพาหนะ ค่าใช้จ่าย และอนุมัติรายการสำคัญ

## FR-01 ระบบเข้าสู่ระบบและจัดการผู้ใช้

### รายละเอียด

ระบบต้องมีการเข้าสู่ระบบก่อนใช้งาน และกำหนดสิทธิ์ตามบทบาทของผู้ใช้

### ความสามารถที่ต้องมี

1. ผู้ใช้สามารถเข้าสู่ระบบด้วยอีเมลและรหัสผ่าน
2. ระบบสามารถออกจากระบบได้
3. Admin สามารถเพิ่ม แก้ไข ปิดใช้งานผู้ใช้ได้
4. Admin สามารถกำหนดบทบาทผู้ใช้ได้
5. ผู้ใช้แต่ละบทบาทเห็นเมนูไม่เหมือนกันตามสิทธิ์
6. ระบบต้องป้องกันผู้ใช้ที่ไม่มีสิทธิ์เข้าหน้าต้องห้าม
7. ระบบต้องบันทึกประวัติการเข้าสู่ระบบ

### Acceptance Criteria

* ผู้ใช้ที่ไม่ได้ Login ต้องไม่สามารถเข้าหน้าหลังบ้านได้
* ผู้ใช้ Role ช่าง ต้องไม่สามารถจัดการผู้ใช้ได้
* ผู้ใช้ Role คลังอะไหล่ ต้องไม่สามารถอนุมัติปิดงานซ่อมได้
* Admin ต้องสามารถจัดการผู้ใช้ได้ครบถ้วน

## FR-02 Dashboard ภาพรวม

### รายละเอียด

Dashboard ต้องแสดงภาพรวมของระบบในหน้าเดียว เพื่อให้ผู้ดูแลเห็นสถานะยานพาหนะและงานซ่อมได้ทันที

### ข้อมูลที่ต้องแสดง

1. จำนวนยานพาหนะทั้งหมด
2. จำนวนรถพร้อมใช้งาน
3. จำนวนรถกำลังซ่อม
4. จำนวนรถรออะไหล่
5. จำนวนรถใกล้ถึงรอบซ่อม
6. จำนวนรถเกินรอบซ่อม
7. จำนวนงานซ่อมรออนุมัติ
8. จำนวนงานซ่อมค้าง
9. ค่าใช้จ่ายซ่อมเดือนนี้
10. อะไหล่ใกล้หมด

### Chart ที่ควรมี

1. กราฟจำนวนงานซ่อมแยกตามสถานะ
2. กราฟค่าใช้จ่ายซ่อมรายเดือน
3. กราฟประเภทรถที่ซ่อมบ่อย
4. ตารางรถที่ใกล้ถึงรอบซ่อม
5. ตารางงานซ่อมเร่งด่วน
6. ตารางอะไหล่ใกล้หมด

### Acceptance Criteria

* Dashboard ต้องโหลดข้อมูลจากฐานข้อมูลจริง
* ตัวเลขบน Card ต้องตรงกับข้อมูลในระบบ
* สามารถกดจาก Card ไปยังหน้ารายละเอียดได้
* กราฟต้องแสดงข้อมูลตามช่วงเวลาที่เลือกได้

### ข้อมูลที่ต้องเก็บ

6. ประเภทยานพาหนะ
7. ยี่ห้อ
8. รุ่น

10. ปีที่เข้าประจำการ

13. ประเภทเชื้อเพลิง

15. ชั่วโมงเครื่องยนต์ ถ้ามี

### สถานะยานพาหนะ

3. ใกล้ถึงรอบซ่อม

6. รออะไหล่

8. ปลดประจำการ

* สามารถเพิ่มรถใหม่ได้
* เลขทะเบียนต้องไม่ซ้ำกัน
* สามารถค้นหารถจากทะเบียน รหัสรถ หรือหน่วยงานได้
* สามารถกรองรถตามสถานะและประเภทรถได้
* สามารถอัปโหลดรูปภาพรถได้
* สามารถดูประวัติซ่อมของรถแต่ละคันได้

## FR-04 ระบบจัดการประเภทยานพาหนะ

2. รถบรรทุก
3. รถตู้
4. รถจักรยานยนต์
5. รถโดยสาร
6. รถพยาบาล
7. รถเฉพาะกิจ
8. รถส่วนกลาง

### ความสามารถที่ต้องมี

1. เพิ่มประเภทรถ
2. แก้ไขประเภทรถ
3. ปิดใช้งานประเภทรถ
4. แสดงจำนวนรถในแต่ละประเภท

### Acceptance Criteria

* ไม่สามารถลบประเภทรถที่มีรถใช้งานอยู่ได้
* สามารถปิดใช้งานประเภทรถแทนการลบได้
* ประเภทรถต้องถูกนำไปใช้ในฟอร์มลงทะเบียนรถได้

## FR-05 ระบบ QR Code ประจำรถ

### รายละเอียด

รถแต่ละคันต้องมี QR Code สำหรับเปิดหน้ารายละเอียดรถอย่างรวดเร็ว

### ความสามารถที่ต้องมี

1. สร้าง QR Code อัตโนมัติเมื่อเพิ่มรถ
2. ดาวน์โหลด QR Code ได้
3. สแกน QR Code แล้วเปิดหน้า Vehicle Detail
4. ผู้ใช้ที่มีสิทธิ์สามารถแจ้งซ่อมจากหน้า QR ได้
5. ผู้ใช้ที่มีสิทธิ์สามารถตรวจสภาพก่อนใช้งานจากหน้า QR ได้

### Acceptance Criteria

* รถทุกคันต้องมี QR Code
* QR Code ต้องเปิดหน้ารถที่ถูกต้อง
* ผู้ใช้ที่ไม่มีสิทธิ์ต้องไม่เห็นปุ่มจัดการสำคัญ

## FR-06 ระบบตรวจสภาพก่อนใช้งาน

ผู้ใช้งานรถหรือพลขับสามารถตรวจสภาพรถก่อนนำไปใช้งานผ่านมือถือหรือ Web App ได้

### รายการตรวจสอบพื้นฐาน

1. น้ำมันเครื่อง
2. น้ำหล่อเย็น
3. น้ำมันเบรก
4. ระบบเบรก
5. ไฟหน้า
6. ไฟท้าย
7. ไฟเลี้ยว
8. ยางรถ
9. แบตเตอรี่
10. แตร
11. กระจก
12. เข็มขัดนิรภัย
13. รอยรั่ว
14. ความเสียหายภายนอก
15. ระดับน้ำมันเชื้อเพลิง

### ผลการตรวจ

1. ผ่าน
2. พบปัญหาเล็กน้อย
3. ไม่ผ่าน / ห้ามใช้งาน

### ความสามารถที่ต้องมี

1. สร้างแบบตรวจสภาพ
2. บันทึกผลตรวจแต่ละรายการ
3. แนบรูปประกอบปัญหา
4. บันทึกเลขไมล์ขณะตรวจ
5. หากผลตรวจไม่ผ่าน ระบบสร้างใบแจ้งซ่อมอัตโนมัติ
6. ดูประวัติการตรวจสภาพย้อนหลังได้

### Acceptance Criteria

* ผู้ใช้สามารถตรวจสภาพผ่านมือถือได้
* หากเลือก “ไม่ผ่าน” ต้องบังคับกรอกหมายเหตุ
* หากตรวจไม่ผ่าน ระบบต้องสร้าง Repair Request ได้
* ประวัติการตรวจต้องเชื่อมกับรถคันนั้น

## FR-07 ระบบรอบซ่อมบำรุง

### รายละเอียด

ระบบต้องสามารถกำหนดรอบซ่อมบำรุงของรถแต่ละประเภทหรือรถแต่ละคันได้

### ประเภทของรอบซ่อม

1. ตามระยะเวลา เช่น ทุก 3 เดือน หรือ 6 เดือน
2. ตามเลขไมล์ เช่น ทุก 5,000 กิโลเมตร
3. ตามชั่วโมงเครื่องยนต์ เช่น ทุก 250 ชั่วโมง

### ตัวอย่างงานซ่อมบำรุง

1. เปลี่ยนน้ำมันเครื่อง
2. เปลี่ยนไส้กรองน้ำมันเครื่อง
3. ตรวจระบบเบรก
4. ตรวจระบบไฟ
5. ตรวจช่วงล่าง
6. ตรวจยาง
7. ตรวจแบตเตอรี่
8. ตรวจระบบหล่อเย็น
9. ตรวจสภาพประจำปี

### ความสามารถที่ต้องมี

1. สร้างแผนซ่อมบำรุง
2. กำหนดรอบตามเวลา เลขไมล์ หรือชั่วโมงเครื่องยนต์
3. ผูกแผนซ่อมกับประเภทรถหรือรถรายคัน
4. ระบบคำนวณรอบถัดไปอัตโนมัติ
5. ระบบแจ้งเตือนเมื่อใกล้ถึงรอบ
6. ระบบแจ้งเตือนเมื่อเกินรอบ
7. ระบบสร้าง Work Order จากรอบซ่อมได้

### Acceptance Criteria

* ระบบต้องคำนวณรอบซ่อมถัดไปได้
* รถที่ใกล้ถึงรอบซ่อมต้องแสดงบน Dashboard
* รถที่เกินรอบซ่อมต้องถูกทำเครื่องหมายชัดเจน
* สามารถสร้างใบงานซ่อมจากรอบซ่อมได้

### รายละเอียด

ผู้ใช้งานสามารถแจ้งปัญหาหรืออาการเสียของรถเข้าสู่ระบบได้

### ข้อมูลที่ต้องเก็บ

1. เลขที่ใบแจ้งซ่อม
2. รถที่แจ้งซ่อม
3. ผู้แจ้ง
4. วันที่แจ้ง
5. อาการเสีย
6. ระบบที่เกี่ยวข้อง เช่น เครื่องยนต์ เบรก ไฟฟ้า ช่วงล่าง
7. ระดับความเร่งด่วน
8. เลขไมล์ตอนแจ้ง
9. สถานที่พบปัญหา
10. รูปภาพหรือวิดีโอประกอบ
11. สถานะใบแจ้งซ่อม
12. หมายเหตุ

2. ปานกลาง

4. ฉุกเฉิน

### สถานะใบแจ้งซ่อม

1. รอรับเรื่อง
2. รับเรื่องแล้ว
3. รออนุมัติ
4. สร้างใบงานแล้ว
5. ยกเลิก

### Acceptance Criteria

* ผู้ใช้สามารถแจ้งซ่อมได้
* ต้องเลือกยานพาหนะก่อนแจ้งซ่อม
* ต้องกรอกอาการเสีย
* สามารถแนบรูปได้
* เจ้าหน้าที่สามารถเปลี่ยนสถานะใบแจ้งซ่อมได้
* สามารถแปลงใบแจ้งซ่อมเป็น Work Order ได้

3. มอบหมายช่างแล้ว
4. กำลังวินิจฉัย
5. รออะไหล่
6. กำลังซ่อม
7. รอตรวจคุณภาพ
8. ซ่อมเสร็จ
9. ปิดงาน
10. ยกเลิก

### ข้อมูลที่ต้องเก็บ

1. เลขที่ใบงาน
2. รถที่ซ่อม
3. อ้างอิงใบแจ้งซ่อม
4. ช่างผู้รับผิดชอบ
5. หัวหน้าช่าง
6. อาการเสีย
7. สาเหตุที่พบ
8. วิธีการซ่อม
9. อะไหล่ที่ใช้
10. ค่าอะไหล่
11. ค่าแรง
12. ค่าใช้จ่ายรวม
13. วันที่เริ่มซ่อม
14. วันที่ซ่อมเสร็จ
15. ระยะเวลาที่รถหยุดใช้งาน
16. รูปก่อนซ่อม
17. รูปหลังซ่อม
18. หมายเหตุ

### Acceptance Criteria

* สามารถสร้าง Work Order จาก Repair Request ได้
* สามารถมอบหมายช่างได้
* ช่างสามารถอัปเดตสถานะงานซ่อมได้
* สามารถบันทึกสาเหตุ วิธีซ่อม และอะไหล่ที่ใช้ได้
* เมื่อปิดงาน ระบบต้องอัปเดตสถานะรถเป็นพร้อมใช้งาน
* ประวัติงานซ่อมต้องแสดงในหน้ารายละเอียดรถ

## FR-10 ระบบคลังอะไหล่

6. จำนวนขั้นต่ำ
7. หน่วยนับ
8. ราคาต่อหน่วย
9. สถานที่จัดเก็บ

2. ไส้กรอง

5. ผ้าเบรก
6. หลอดไฟ
7. สายพาน
8. ช่วงล่าง
9. ระบบไฟฟ้า

3. รับอะไหล่เข้า

8. คำนวณต้นทุนอะไหล่ในใบงานซ่อม

* ไม่สามารถเบิกเกินจำนวนคงเหลือได้
* หากจำนวนคงเหลือต่ำกว่าจำนวนขั้นต่ำ ต้องแจ้งเตือน
* การใช้อะไหล่ใน Work Order ต้องถูกบันทึกเป็นต้นทุนงานซ่อม

## AI-01 AI สรุปประวัติซ่อมรถ

### รายละเอียด

ระบบต้องมีปุ่มให้ผู้ใช้สรุปประวัติซ่อมของรถแต่ละคันด้วย AI

### Input

1. ข้อมูลรถ
2. ประวัติงานซ่อม
3. รายการอะไหล่ที่ใช้
4. ค่าใช้จ่ายซ่อม
5. ระยะเวลาหยุดใช้งาน

### Output

AI ต้องสรุปเป็นภาษาที่เข้าใจง่าย เช่น

1. จำนวนครั้งที่ซ่อม
2. ปัญหาที่พบซ้ำ
3. ค่าใช้จ่ายรวม
4. แนวโน้มความเสี่ยง
5. คำแนะนำเบื้องต้น

### Acceptance Criteria

* AI ต้องไม่แก้ไขข้อมูลในฐานข้อมูลเอง
* AI ต้องแสดงผลเป็นคำแนะนำเท่านั้น
* หาก AI ใช้งานไม่ได้ ต้องแสดงข้อความ fallback
* ผู้ใช้ต้องสามารถกดสร้างสรุปใหม่ได้

---

## AI-02 AI วิเคราะห์อาการเสีย

### รายละเอียด

เมื่อผู้ใช้กรอกอาการเสีย ระบบสามารถให้ AI วิเคราะห์เบื้องต้นได้

### Input

ข้อความอาการเสีย เช่น
“เบรกจม มีเสียงดังตอนเหยียบเบรก และรถหยุดช้ากว่าปกติ”

### Output

1. ระบบที่เกี่ยวข้อง
2. ระดับความเร่งด่วนที่แนะนำ
3. คำแนะนำเบื้องต้น
4. ข้อควรระวัง

### Acceptance Criteria

* AI ต้องระบุว่าเป็นเพียงคำแนะนำเบื้องต้น
* ผู้ใช้สามารถแก้ระดับความเร่งด่วนเองได้
* ระบบต้องไม่ใช้ AI แทนการตัดสินใจของช่าง

---

## AI-03 AI สร้างสรุปรายงานประจำเดือน

### รายละเอียด

ผู้ดูแลสามารถกดให้ AI สรุปรายงานภาพรวมประจำเดือนได้

### Input

1. จำนวนงานซ่อมทั้งหมด
2. งานซ่อมเสร็จ
3. งานค้าง
4. ค่าใช้จ่ายรวม
5. รถที่ซ่อมบ่อย
6. อะไหล่ที่ใช้บ่อย
7. รถที่เกินรอบซ่อม

### Output

AI ต้องสร้างสรุปเป็นข้อความ เช่น

1. ภาพรวมประจำเดือน
2. ปัญหาสำคัญ
3. ค่าใช้จ่าย
4. รถที่ควรติดตาม
5. ข้อเสนอแนะ

### Acceptance Criteria

* AI ต้องสร้างรายงานจากข้อมูลที่ระบบส่งให้เท่านั้น
* หาก AI ไม่พร้อมใช้งาน ระบบต้องสร้างสรุปแบบ Rule-based ได้
* รายงานที่ AI สร้างต้องสามารถคัดลอกหรือนำไปใช้ในรายงานได้

---

## AI-04 AI Fallback

### รายละเอียด

หาก AI Server ไม่พร้อมใช้งาน ระบบต้องไม่ล่ม และต้องใช้ Rule-based Logic แทน

### ตัวอย่าง Rule-based Logic

1. ถ้ารถเกินรอบซ่อม ให้แจ้งเตือนทันที
2. ถ้างานซ่อมค้างเกิน 7 วัน ให้แจ้งเตือนหัวหน้าช่าง
3. ถ้าอะไหล่ต่ำกว่าจุดขั้นต่ำ ให้แจ้งเตือนคลัง
4. ถ้ารถซ่อมระบบเดิมซ้ำ 3 ครั้งใน 6 เดือน ให้แสดงสถานะเสี่ยง

### Acceptance Criteria

* ระบบหลักต้องทำงานได้แม้ AI Server ปิดอยู่
* หน้าเว็บต้องไม่ Error เมื่อเรียก AI ไม่สำเร็จ
* ต้องแสดงข้อความว่าใช้ Rule-based Summary แทน AI

# 11. Non-Functional Requirements

## NFR-01 ความปลอดภัย

1. ต้องมีระบบ Authentication
2. ต้องมี Role-Based Access Control
3. Password ต้องถูก Hash ก่อนเก็บ
4. API ต้องตรวจสอบสิทธิ์ทุกครั้ง
5. ผู้ใช้ไม่มีสิทธิ์ต้องเข้าถึงข้อมูลต้องห้ามไม่ได้
6. File Upload ต้องจำกัดชนิดไฟล์
7. ต้องมี Audit Log สำหรับการกระทำสำคัญ

---

## NFR-02 ประสิทธิภาพ

1. Dashboard ควรโหลดภายในเวลาที่เหมาะสม
2. ตารางข้อมูลต้องรองรับ Pagination
3. การค้นหาควรตอบสนองเร็ว
4. รูปภาพควรถูกบีบอัดก่อนแสดงผล
5. AI ต้องทำงานแบบกดเรียกใช้งาน ไม่รันอัตโนมัติทุกครั้งที่เปิดหน้า

---

## NFR-03 การใช้งานบนมือถือ

1. ระบบต้องรองรับ Responsive Design
2. หน้าแจ้งซ่อมต้องใช้งานง่ายบนมือถือ
3. หน้า Check Inspection ต้องเหมาะกับมือถือ
4. ปุ่มสำคัญต้องกดง่าย
5. ตารางขนาดใหญ่ต้องแสดงผลแบบ Responsive

---

## NFR-04 ความน่าเชื่อถือ

1. ระบบต้องไม่ล่มเมื่อ AI ใช้งานไม่ได้
2. การบันทึกข้อมูลต้องมี Validation
3. ต้องป้องกันการกรอกข้อมูลซ้ำ
4. ต้องมี Error Message ที่เข้าใจง่าย
5. ควรมีระบบ Backup ฐานข้อมูลในอนาคต

## NFR-05 การขยายระบบ

1. ระบบต้องแยกโมดูลชัดเจน
2. AI Module ต้องเปลี่ยนโมเดลได้ในอนาคต
3. Database Schema ต้องรองรับการเพิ่มฟีเจอร์ใหม่
4. Code ต้องจัดโครงสร้างให้ดูแลรักษาง่าย
5. ควรแยก Business Logic ออกจาก UI Component

# 15. Main Workflow

## 15.1 Workflow การแจ้งซ่อม

1. ผู้ใช้เลือกยานพาหนะ
2. กรอกอาการเสีย
3. แนบรูปประกอบ
4. ระบบบันทึกใบแจ้งซ่อม
5. เจ้าหน้าที่ยานยนต์ตรวจสอบ
6. หากอนุมัติ ระบบสร้าง Work Order
7. หัวหน้าช่างมอบหมายช่าง
8. ช่างตรวจสอบและซ่อม
9. หากต้องใช้อะไหล่ ให้ขอเบิกอะไหล่
10. คลังอะไหล่อนุมัติและตัดสต็อก
11. ช่างซ่อมเสร็จและแนบรูปหลังซ่อม
12. หัวหน้าช่างตรวจคุณภาพ
13. ปิดงานซ่อม
14. ระบบอัปเดตสถานะรถ

---

## 15.2 Workflow รอบซ่อมบำรุง

1. Admin หรือเจ้าหน้าที่ยานยนต์สร้าง Maintenance Plan
2. กำหนดรอบซ่อมตามเวลา เลขไมล์ หรือชั่วโมงเครื่องยนต์
3. ผูกแผนกับรถหรือประเภทรถ
4. ระบบคำนวณวันหรือเลขไมล์รอบถัดไป
5. เมื่อใกล้ถึงรอบ ระบบแจ้งเตือน
6. หากเกินรอบ ระบบเปลี่ยนสถานะเป็นเกินรอบซ่อม
7. เจ้าหน้าที่สร้าง Work Order จากรอบซ่อม
8. ช่างดำเนินการซ่อมบำรุง
9. ปิดงาน
10. ระบบคำนวณรอบถัดไปใหม่

---

## 15.3 Workflow การเบิกอะไหล่

1. ช่างเลือก Work Order
2. ช่างเลือกอะไหล่ที่ต้องใช้
3. ระบบตรวจสอบจำนวนคงเหลือ
4. หากเพียงพอ ส่งคำขอเบิก
5. เจ้าหน้าที่คลังอนุมัติ
6. ระบบตัดจำนวนคงเหลือ
7. ระบบบันทึกต้นทุนใน Work Order
8. หากอะไหล่ต่ำกว่าจุดขั้นต่ำ ระบบแจ้งเตือน

# 20. สรุป Requirement

Smart Army Vehicle Maintenance Dashboard เป็นระบบ Web Application สำหรับบริหารจัดการยานพาหนะและงานซ่อมบำรุงแบบครบวงจร โดยมีฟีเจอร์หลักคือ Dashboard, Vehicle Registry, Maintenance Schedule, Repair Request, Work Order, Parts Inventory, Reports และ AI Assistant

ระบบนี้ออกแบบให้ใช้งานได้จริงในลักษณะงานสนับสนุนและงานบริหารจัดการ โดย AI เป็นเพียงโมดูลเสริม ไม่ใช่ส่วนบังคับของระบบ หาก AI ไม่พร้อมใช้งาน ระบบยังสามารถทำงานด้วย Rule-based Logic ได้

โครงการนี้เหมาะสำหรับนำเสนอเป็นโครงงาน Web Application เพราะมีขอบเขตชัดเจน มีปัญหาที่สมเหตุสมผล มีผู้ใช้งานหลายบทบาท มีฐานข้อมูลหลายส่วน มี Dashboard และสามารถต่อยอดสู่ระบบจริงในอนาคตได้
